## Frontend dependency review and integration boundary

The imported Core frontend manifest pins `home-assistant-frontend==20261028.4`. The matching upstream `home-assistant/frontend` tag `20261028.4` resolves to `a67b691a451e0b3fc469679b07158f963a61842c`, and its `LICENSE.md` is Apache-2.0. At this tag, `package.json` declares Node.js `24.22.1`, pnpm `12.15.0`, `postinstall: husky`, `prepack/postpack: pinst`, and a build manager that launches Gulp. The workspace config specifies `minimumReleaseAge`, `trustPolicy: no-downgrade`, a dependency build-script allowlist, and several patched dependencies. These are source-level findings, **not** a completed malware review, dependency audit, or frontend build.

The next compatible implementation boundary is a **separately pinned, independently built frontend**, with upstream licenses and other assets reviewed before any changes to the Core frontend requirement. The GC UI styling, identity, navigation, and UI states must be implemented and screenshot-reviewed on that frontend branch; do not substitute a renamed Python package or an unvalidated CSS injection for a complete runtime rebrand. Protect existing websocket/auth contracts, user configurations, Lovelace dashboards, and device integrations while a separate frontend is tested. Do not execute package install hooks or modified build scripts without source and dependency review.

### Assist audio native-library compatibility (November 8, 2026)

A source-level review of `homeassistant/components/assist_pipeline/audio_enhancer.py` found **two** independent pinned dependency problems. The imported Assist pipeline calls `MicroVad.Process10ms(audio)` and `AudioProcessor.Process10ms(audio).audio`. The upstream-generated `requirements.txt`, `requirements_all.txt`, `homeassistant/package_constraints.txt` and Assist manifest pin `pymicro-vad==1.0.1` and `pyspeex-noise==1.0.2`. The former lacks CPython 3.14 wheels on PyPI; the latter publishes only a source distribution. The resulting direct-wheel failure is therefore not a single-package problem.

Upstream `pymicro-vad==2.1.0` (Apache) and `pyspeex-noise==2.0.1` (MIT) publish Linux x86-64 and ARM64 `cp39-abi3` wheels. **Their Python APIs are different:** `MicroVad.process_10ms(audio)` replaces the legacy capitalized method; `AudioProcessor.process_10ms(audio)` returns **bytes**, unlike the legacy `.Process10ms(audio).audio` shape. A blind pin change would break Assist; those releases are potential **Linux-specific candidates**, not approved all-platform drop-ins.

The `audio_compat.py` bridge retains both recognized API shapes without touching current pins. Dependency-free synthetic tests verify return-value handling, modern/legacy dispatch and missing-method failures; a Python 3.14 syntax check covers the actual consumer. **Native input safety finding:** inspected upstream `pyspeex-noise` 2.0.1 `src/speex_noise.cpp` copies a fixed 320-byte frame without checking the input buffer length. Python `assert len(audio) == 320` in the existing consumer is insufficient when assertions are disabled. The bridge now applies unconditional type and exact 320-byte frame validation before calling either native method, and validates processed Speex output size; negative tests verify that short and oversized inputs never reach synthetic native callbacks. This is a targeted local safeguard, **not** a complete native C++ memory-safety audit. These tests do not execute third-party native libraries or simulate live audio accuracy. Actual candidate version adoption still requires source/dependency/security review, exact wheel and license verification, supported-platform checks, real 10 ms audio behavior tests, and consistent regeneration of all four version-pin locations. Do not claim full Python 3.14 dependency resolution based on this bridge.

## GoreeCloud UI authority

The design authority is [GoreeCloud UI](https://github.com/GoreeCloud/gc-ui), not the imported upstream frontend. The active design-language standard and semantic tokens govern any future GoreeCloud-controlled screens. Stable Foundations v1.0.1 is scoped to semantic tokens, color, and browser-theme control; it does **not** confer stability on the rest of the experimental component workspace or certify this product.

- Use **GoreeCloud Home Manager** as the full public product name, while keeping existing Home Assistant backend integration identifiers where needed for compatibility.
- Reuse verified GC UI semantic tokens and theme behavior only after resolving the upstream frontend's independent build, licensing, packaging, and configuration interfaces.
- Do not invent mandatory GoreeCloud brand colors. Design choices must retain semantic contrast, keyboard/assistive usability, reduced-motion options, and responsive behavior.
- Inspect rendered login, onboarding, dashboards, automations, devices, integrations, settings, update/error/empty states, and mobile layouts before claiming a complete rebrand.
- Third-party Home Assistant, Open Home Foundation, and device/vendor marks must be reviewed separately; do not imply endorsement.

### Pinned PyTurboJPEG 1.8.3 source provenance review

The inherited camera and stream integrations use `PyTurboJPEG==1.8.3` and specifically call `TurboJPEG.decode_header(jpeg_bytes)` and `TurboJPEG.scale_with_quality(jpeg_bytes, scaling_factor=..., quality=...)`. This release has a **source distribution only on PyPI**, so a strict binary-only direct dependency probe cannot install it. The upstream repository tag [`v1.8.3`](https://github.com/lilohuang/PyTurboJPEG/tree/v1.8.3) contains a small `setup.py` declaring a Python wrapper `turbojpeg.py` and NumPy as its runtime requirement, plus an MIT copyright notice. This Python package dynamically loads an external **libjpeg-turbo 2.x** system library; a pure Python wheel is therefore not a standalone native library or a security certification. The Ubuntu 24.04 system's documented libjpeg-turbo version is 2.1.5. The newer PyTurboJPEG 2.x package requires libjpeg-turbo 3.x instead, so simply upgrading its version would break the 24.04 system-library compatibility assumption.

The [inert source provenance gate](https://github.com/GoreeCloud/home-manager/pull/15) compares the official PyPI `pyturbojpeg-1.8.3.tar.gz` SHA-256 `c131591a3990cc57f45a8b2705d6261c25df913a19b1fe88de5e911dbe04a1d4`, safe TAR member properties, and the `setup.py`, `turbojpeg.py`, and MIT `LICENSE` contents against the reviewed upstream tag's Git blobs, **without extraction, installation or executing its source**. A passing result would establish source identity only. An independently bounded, disposable wheel build and JPEG function tests must be separately reviewed before any reliance on this package as a Python 3.14 installation solution.

### Linux candidate transitive resolver rehearsal — review-only

The imported Core release pins **56 exact direct packages** and four version ranges on Python 3.14.10 Linux, with three source-only or incompatible original direct wheel artifacts. This prevents an unmodified all-binary install. To move toward a reproducible solve without committing unverified new Core pins, the [review-only candidate resolver PR](https://github.com/GoreeCloud/home-manager/pull/18) creates an **ephemeral copy** of imported `requirements.txt` and `homeassistant/package_constraints.txt` (with source SHA-256 values recorded). It changes **only** the two previously inspected and synthetically tested candidate native audio versions (`pymicro-vad==2.1.0`, `pyspeex-noise==2.0.1`), retaining `PyTurboJPEG==1.8.3`. The original requirement, manifest and constraints files remain byte-identical. The original PyTurboJPEG pure-Python wheel is built only from tag- and PyPI-hash-matched files with a verified setuptools backend as in PRs #15–#16. A separately SHA-256-pinned `uv==0.13.6` official wheel (already listed in upstream Core requirements) is used **only** inside a temporary hosted CI virtual environment to resolve package metadata using `uv pip compile` with uv 0.13.6-compatible `--no-build`, `--no-cache`, an explicit public PyPI index, the temporary original-version PyTurboJPEG wheel, and Python 3.14.10 targeting. The solver is not given private credentials or access to household systems. Outputs remain on the ephemeral runner and **do not constitute a production lockfile**.

**Solver flag compatibility:** Hosted [first review run 42517709306](https://github.com/GoreeCloud/home-manager/actions/runs/42517709306) showed that uv 0.13.6 rejects combining `--no-build` with `--only-binary`. The job now uses **`--no-build --no-cache`** to prevent executing source builds and to exclude previously built cache artifacts. Metadata resolution may still query source-release *metadata*; no source archive is installed or built by the solver. The original pinned constraints remain unchanged in Git.

**Candidate resolver evidence, November 8, 2026:** [Initial full candidate run](https://github.com/GoreeCloud/home-manager/actions/runs/42517709306) stopped on a uv CLI flag conflict, which was corrected without weakening source-build prevention. The [next run](https://github.com/GoreeCloud/home-manager/actions/runs/42517804198) reached the transitive dependency solver. Uv reported a **new, exact no-wheel blocker**: `home-assistant-bluetooth==2.0.0` requires `habluetooth==7.1.2`, then `bluetooth-auto-recovery==1.6.4`, then `pyric>=0.1.6.3`. PyPI offers `PyRIC==0.1.6.3` as a **2016 source distribution only** (SHA-256 `b539b01cafebd2406c00097f94525ea0f8ecd1dd92f7731f43eac0ef16c2ccc9`), explicitly labeled **GPLv3**, with functionality for inspecting and modifying Linux wireless interfaces. The upstream `wraith-wireless/PyRIC` repository's currently available tags stop at `0.1.6` rather than providing an exact `0.1.6.3` tag; the current `master` describes `0.1.6.4`. Neither upstream HEAD nor a third-party wheel mirror is a verified equivalent to the pinned release. **Do not install or execute this source on household devices or CI merely to satisfy the solver.** Audit its exact source, provenance, imported use, setup/import effects, GPL/compliance implications and permission requirements before any isolated source-build proposal.

The review CI now treats this **specific documented error** as a *successful diagnostic finding only* and retains `full_dependency_graph_solved: false`. Any other failure, timeout or unrecognized dependency error fails CI. The source requirements and production release gate remain unchanged and unresolved.

The uv Rust binary itself is executable third-party software; its PyPI SHA-256, upstream publisher and pinned version do **not** guarantee freedom from vulnerabilities, compromised releases or unsafe network behavior. Execution is confined to a standard, transient first-party GitHub-hosted runner with read-only GitHub permissions and no sensitive project secrets. A resolver failure must remain a **diagnostic blocker** with its precise conflict reported; changing additional pins or bypassing binary-only restrictions is not implicitly authorized. ### Direct-wheel metadata inventory acceptance boundary

The first-party, branch-only/manual inventory analyzes `requirements.txt` exactly as imported, retaining its upstream constraints declaration. It parses only normalized package metadata and exact `==` pins; range constraints are listed as unassessed. For each exact pin it retrieves bounded JSON release metadata from `https://pypi.org/pypi/`, checks non-yanked wheel filenames, advertised SHA-256 metadata, `Requires-Python`, and wheel tags against the GitHub runner's Python 3.14.10 Linux host tags. It records pin status to a short-lived runner-local JSON file and prints only package names, versions, classifications, and totals. Queries are concurrent but capped at six workers. **No distribution wheel, sdist, installation hook, native extension, or Home Assistant runtime is downloaded or executed by this inventory**. Existence of PyPI metadata does not verify artifact hashes, trustworthiness, supported platform range, dependency graph resolution or application functionality. Missing metadata and network failures must remain explicitly unverified, not silently treated as supported packages.
